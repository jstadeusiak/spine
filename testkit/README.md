# Application conformance fixtures

`ApplicationConformance` is a public, cold test fixture. Supply an application factory, its identity, a log ID and
exact encoded proposal bytes with logged nanosecond timestamps. It compares complete receipts, canonical events
and snapshots across repeated runs and every restore cut. It checks exact retries at changed timestamps and
verifies that truncated or corrupted snapshots leave live state unchanged. It allocates freely and measures no latency.

```java
var report = ApplicationConformance.verify(
    CounterApplication::new, CounterApplication.IDENTITY, CounterExample.LOG_ID, CounterExample.corpus());
```

For explicit capacity declarations, use `verify(factory, identity, limits, logId, commands)` with the application's
`ApplicationLimits`. The same checks cover variable SBE batches and compact cached-result snapshots. A generated
repeating-group counter fixture exercises this overload; application authors still own batch framing and validation.

The neutral `CounterApplication` owns one nonnegative total. Negative, malformed and overflowing additions produce
deterministic application rejections. Its schema, identity `(501, 1, 1)`, output and snapshot are independent of
Binance. Generated SBE codecs live in the test-fixture artifact; the application transition and snapshot encoder
reuse their buffers and flyweights. Tests check literal expected bytes and strict warmed zero allocation with a
negative control. Cold restore and this conformance harness have separate allocation budgets.

The full corpus has a separate [Python struct oracle](src/test/python/counter_oracle.py), built from fixed logical
facts without running Spine or its generated codecs. Its retained command/time, canonical and complete snapshot
bytes are in [test resources](src/test/resources/counter-oracle/expected.json). Tests require the exact output and
snapshot digests on every supported Java version; expected fixtures are never regenerated by the test task.
The current snapshot oracle includes variable-length result receipts. The retained
[initial-release reports](../docs/evidence/1.0.0/README.md) describe the earlier fixed-receipt baseline.

```sh
./gradlew :testkit:test :testkit:conformance
```

The runnable example includes two producers, a duplicate, domain rejections and a protocol sequence gap. Its report
is written to `testkit/build/reports/conformance/counter.json`. Add application-specific independent oracles, capacity
and failure cases to your corpus; repeated equality alone does not establish that business behavior is correct.

From a separate Gradle application, consume the staged test-fixture variant:

```kotlin
dependencies {
    testImplementation(testFixtures("spine:testkit:1.0.0"))
}
```

The fixture depends on generic Spine APIs and has no Binance dependency. See [local publication staging](../docs/releasing.md).
The retained [publication consumer](src/test/publication-consumer/check.py) compiles and executes an independent
temporary Gradle application against those staged artifacts; CI runs it on Java 21 and 25.
